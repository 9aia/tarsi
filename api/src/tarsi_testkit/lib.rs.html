1//! tarsi-testkit — the behavioral backbone for tarsi's ports and
2//! the `tarsi-serve` op surface (PL-014 B3/D5):
3//!
4//! - [`fixtures`] — commit-range JSON fixtures exercising every
5//!   bump class; [`fixtures::synthetic_commits`] parses them into
6//!   [`tarsi_core::commit::Commit`]s.
7//! - [`golden`] — golden plan cases: specs + commits → expected
8//!   bump/version/tag/changelog per unit. [`GoldenCase::check`]
9//!   diffs a [`tarsi_core::ReleasePlan`] against the expectation —
10//!   the spec the legacy TS behavior maps onto (B3). Cases cover
11//!   synthetic ranges plus one real org range (tarsi's own
12//!   `crates/tarsi-serve` history).
13//! - [`repo`] — real-git fixture builders: temp workspace repos
14//!   (multi-unit cargo workspace, bare `origin`, conventional
15//!   commits, tags) for anything that must exercise `lasius-vcs`
16//!   for real.
17//! - [`serve`] — the `tarsi-serve` op conformance suite: every
18//!   `assert_*` runs one op contract against a `&dyn Vcs` +
19//!   fixture dir, so any VCS impl (or a future serve refactor)
20//!   proves the same wire behavior. [`serve::assert_conformance`]
21//!   runs the read-only ops; [`serve::assert_release_conformance`]
22//!   adds the mutating `release` path (needs `origin` + a
23//!   no-publish `tarsi.toml`).
24//!
25//! Downstream crates consume this as a dev-dependency and call the
26//! `assert_*` functions from their own tests — same pattern as
27//! `scarab-testkit` / `sepia-testkit`.
28
29pub mod fixtures;
30pub mod golden;
31pub mod repo;
32pub mod serve;
33
34pub use fixtures::synthetic_commits;
35pub use golden::{cases as golden_cases, GoldenCase, UnitExpect};
