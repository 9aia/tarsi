tarsi-core — the pure release domain. No I/O, no git, no network: callers feed it commits (from tarsi-vcs) and unit specs (from manifests/config) and get back a ReleasePlan plus rendered changelogs. Everything forge- or VCS-specific lives in the port crates.

Modules§

bump
Semver bump policy — major/minor/patch/none plus the conventional-commit inference that picks one.
changelog
Changelog model: strategy-ordered sections, entries grouped under them, markdown rendering for splicing into CHANGELOG.md. Section identity/order/headings come from the release Strategy — P-030 made the keep-a-changelog section map data, so this module no longer hardcodes Section kinds; the conventional builtin reproduces the old map byte-identically.
commit
Commit model + conventional-commit parsing. A Commit is the VCS-neutral shape tarsi-vcs adapters produce; parsing the subject into a ConventionalCommit is pure.
config
The tarsi.toml/tarsi.yml config model — pure serde types. Loading/discovery lives in scarab-config (FileSource); this module only defines what the file means. Secret names and cuora:// refs appear here (token_env, token_ref); values never do — cuora boundary.
plan
The release plan — pure computation from unit specs + commits. plan_release attributes commits to units by path prefix, infers bumps, topo-sorts publish order, and emits the ordered ReleaseSteps a driver/serve op would execute.
strategy
Release strategies (P-030) — bump inference and changelog sectioning as pure serde data, selectable per repo/profile via [release] strategy in tarsi.toml.
unit
Release-unit spec — one independently-versioned publishable thing in a repo (a cargo workspace member, a single package, or a configured path prefix).
