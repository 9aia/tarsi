Release strategies (P-030) — bump inference and changelog sectioning as pure serde data, selectable per repo/profile via [release] strategy in tarsi.toml.

A Strategy is two rule tables:

  • BumpRules — ordered-agnostic rules[] of {type?, scope?, breaking?, not_type?, bump}. A commit contributes the max bump across its matching rules (semantic-release commit-analyzer’s “highest release type wins”); a unit folds max across its commits. fallback is the bump when inference finds nothing.
  • ChangelogRules — ordered sections[] of {key, heading, rules[]}; table order is both match precedence (first matching section wins) and render order. Commits matching no section are dropped.

Matchers run against the ConventionalCommit’s raw type token (raw_type — deps, i18n, … are nameable, unlike the closed CommitKind enum), its scope, and its breaking flag:

  • type — exact raw-type token, or "*"/absent for any.
  • scope — exact scope, trailing-* prefix glob, or "*"/absent for any (including no scope).
  • breaking — true/false pins the !/BREAKING CHANGE flag; absent matches either.
  • not_type — raw-type tokens that veto the match. This is how conventional expresses “breaking commits of otherwise-silent kinds land in Changed” without stealing fix!/perf!/feat! from their own sections.

Builtin strategies are compile-time data (Strategy::conventional, Strategy::semantic_release_angular); custom strategies are inline TOML/YAML tables — no plugin binaries, no trait objects. What can’t be data (render templates beyond section/heading/order, non-semver versioning, non-conventional parsing, anything needing execution) stays code — see P-030.
