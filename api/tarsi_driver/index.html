tarsi-driver — library half of tamias-driver-tarsi, the tamias content driver for type: tarsi release-profile packs (PL-014 D3).

A type: tarsi pack is a release profile: a payload whose root carries tarsi.{yaml,yml,toml} (a plain tarsi_core::Config document — no [profile] table; profile is the selector key) plus optional extras (styleguide.md, commit maps, …). See tarsi-config’s profile module for the discovery contract this driver installs into.

§Where install places the profile

tamias dispatches install before its store commit, with --dir = the payload root; uninstall/deploy/status get the committed store entry dir (<store>/[@scope/]<name>@<label>/). tarsi’s profile discovery already treats the tamias store as a first-class source — store_profiles finds every <store>/name@label/ carrying a tarsi.* and find_dir picks the newest version label. The store commit is therefore the placement: install validates the payload and reports; the pack becomes resolvable the moment tamias commits it, versioned by label.

The driver deliberately does not copy payloads into ~/.config/tarsi/profiles/<name>/ by default: dir profiles are searched before the store and win find_dir, and they carry no version — an unversioned copy would shadow every store version, including ones tamias remove already dropped (the host only dispatches uninstall on the last same-name sibling, T-029).

Opt-in escape hatch: --config may name a profilesDir. Then install/deploy also materialize an unversioned dir-profile copy at <profilesDir>/<name>/ (scoped names nest @scope/<name>/) stamped with a .tamias-driver-tarsi.json marker, and uninstall removes marker-bearing copies it finds under the profiles roots. Use it to pin a profile outside the evictable store — knowing the copy shadows store resolution.

§Verbs (the tamias driver contract)

<verb> --dir <d> --name <n> [--config <f>]:

  • capabilities — {"capabilities": ["tamias"], "types": ["tarsi"], "verbs": […]}; tamias’s discovery probe.
  • install — validate the payload is a well-formed profile (tarsi.* present and parses as Config; tamias.yaml’s type must be tarsi when present), then optionally write the profilesDir copy. JSON report; nothing else is applied.
  • deploy — refresh the operator-facing state: re-validate the installed entry and re-sync the profilesDir copy when configured; reports how tarsi resolves the name.
  • uninstall — remove marker-bearing profilesDir copies under the profiles roots ($TARSI_PROFILES_DIR, ~/.config/tarsi/profiles, plus the configured dir). The store entry itself is dropped by tamias after this verb returns.
  • status — resolution report: which dir find_dir picks for the name, from which source, and every installed candidate.
  • health — discovery probe: profiles roots + visible profile count. No services exist for a profile pack.
  • logs / hooks — empty reports; type: tarsi packs run no units and declare no forge hooks.
  • config-schema — JSON Schema (draft 2020-12) of the optional --config file (see DriverConfig).

§The pavo read-only surface

The same binary is also a pavo view driver (PL-014 D3 remainder): manifest prints the pavo_protocol::DriverManifest and serve answers ndjson JSON-RPC (manifest/views/view/ query) over views — release plans, changelog previews, and publish-profile state, all read through tarsi-serve one-shot ops (data). The surfaces are disjoint by argv: pavo’s probes (manifest/capabilities/serve) take no --dir/--name, tamias’s verbs always carry them — capabilities answers a merged payload satisfying both discoverers. Nothing on the pavo side mutates: the serve ops called are manifest, profiles, plan, changelog — release is never dispatched.

See views.rs for the view/ query mapping and data.rs for the tarsi-serve invocation ($TARSI_SERVE overrides the binary, default tarsi-serve on PATH).

Modules§

data
data — the pavo read plane. Every query is one tarsi-serve one-shot op (tarsi-serve <op> --dir <d> --set k=v …), the same wire peregrin campaigns and humans use — the driver never opens tarsi state itself (“pavo renders what the serve reports”).
views
views — the driver’s manifest: every ViewSpec plus the query resolvers that feed them (the pavo read-only surface, PL-014 D3 remainder).

One JSON answers both: the kit’s {capabilities, verbs} shape plus "types": ["tarsi"], "tamias" in capabilities, and every verb folded into verbs.

hooks
